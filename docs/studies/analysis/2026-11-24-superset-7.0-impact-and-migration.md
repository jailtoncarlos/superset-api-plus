# Superset 7.0: impact on superset-api-plus and migration options

Based on [the 6.1.0 → 7.0.0rc3 research](../research/2026-11-24-superset-7.0-changes.md), which holds the
Superset sources for every claim. Library paths are relative to `supersetapiplus/` unless they start with `tests/`, `bin/` or `docker`, and
line numbers refer to `main` at 0517a44 (release 2.4.0). 7.0.0 is still a release candidate; items marked **[not verified against a running 7.0]** come from
reading code only.

Compatibility classes: **Breaks** (current behavior fails or is wrong on 7.0); **Breaks conformance** (the
library still works but no longer matches what 7.0's Explore or spec produces); **Compatible** (6.1 and 7.0
can be served at once, usually by detecting the server version with `GET /version`, which returns
`version_string` on both).

**Correction to the source inventory (I-20).** It listed `uuid` on chart/dashboard/dataset POST as new in
7.0. The 6.1.0 code already accepted it (apache/superset@c83fb2b:superset/charts/schemas.py:246); only the
published 6.1.0 spec omitted it. What is new in 7.0 is the `uuid` in the POST **response** (N-07). The
published 6.1.0 spec is incomplete in several places (research, "Scope" and appendix), so any 6.1↔7.0
comparison must be made on the code, not only on the specs.

Checked without impact: no `/superset/...` route is called by the library (only docstrings mention it:
`auth/csrf.py:36`, `charts/charts.py:525`, `exceptions.py:190`, `charts/cal_heatmap.py:28`); form login,
JWT login/refresh and `csrf_token` unchanged; every route the library calls exists in rc3; the 19 modeled
viz types are still registered; roles/permissions, CSS template, saved query and database write schemas
unchanged; layout and native filter constants unchanged; removed async routes unused (`run_query` already
refuses 202); PUT `ETag` without required `If-Match`; tags not sent (`SerializableNotToJson`);
`overwrite_all` defaults to `false`.

## 5. Migration options

**Option A — support 6.1 and 7.0 at once.** `client.server_version` from `GET /version` (T-01); field sets
(`POST_FIELDS`/`PUT_FIELDS`), aliases, buildQuery functions and warnings branch on the version; both
excerpt sets (`*_6.1.0`, `*_7.0.x`) kept and conformance run per version; integration and example tests on
a 6.1 × 7.0 matrix, which needs the maintainer's authorization for CI. Consumers upgrade the library
independently of their server.

**Option B — 2.x for 6.1, 3.0.0 for 7.0.** Tag the last 6.1-targeted release and keep a `2.x` maintenance
branch for 6.1 fixes; move `main` to 7.0 as 3.0.0 with a single target (no version branches, no CI matrix,
one excerpt set). Old names (`owners`, dashboard `roles`, RLS `roles`) stay as deprecated aliases mapped to
the 7.0 fields, because `AGENTS.md` requires public API stability. Consumers on 6.1 stay on 2.x until they
upgrade their server. Work can start on the rc; 3.0.0 is released only after 7.0.0 final, with the excerpts
regenerated on the final tag.

| Criterion | A: 6.1 + 7.0 | B: 2.x (6.1) + 3.0.0 (7.0) |
|---|---|---|
| Code | Version branches in models, buildQuery, warnings, auth defaults; two excerpt sets | Single target; aliases only for renamed fields |
| CI | 6.1 × 7.0 matrix (authorization needed); about twice the integration time | Unchanged shape on `main`; `2.x` runs its own CI only when fixes land |
| Consumers on 6.1 | Same latest release works | Stay on 2.x; fixes must be backported |
| Coupling library ↔ server | Loose: any library version for either server | Tight: major version follows the server |
| Risk now (rc only) | Branches written against an rc may need rework at final | Low: nothing released before 7.0.0 final |
| Cost over time | Grows with each extra supported version | Flat on `main`; backports while 2.x lives |

**Deciding factor:** when the consumers' instances move to 7.0. If they move soon after the final release,
the 2.x branch is short-lived and B pays off. If they stay on 6.1 for long, backporting to 2.x costs about
as much as keeping the branches of A, and A keeps one line of development.

**Decision (2026-11-24, maintainer): Option B.** The 6.1 line is closed with a tag and kept on a `2.x`
branch; `main` moves to 7.0 and is released as 3.0.0 after 7.0.0 final. All tasks of section 4 are opened
now, starting with those that do not depend on the final tag: feature #53, with one sub-issue per task
(T-01 #54 … T-20 #73, in order).

## 6. Not verified and limitations

- Nothing was run against a 7.0 server: N-01/session mode, N-02 (API key route, CSRF on writes, public
  endpoints), I-09 (`type_generic` 4 read back), I-15 (CSRF text), I-18 (marshmallow 4 messages), I-19
  (403 vs redirect), N-03 `extra_form_data` details, N-04 response shapes.
- No 7.0 UI capture was generated (`ui_references`, `ui_query_contexts`, `ui_defaults`, `ui_controls`,
  `example_layouts`); I-06..I-08 and N-12 come from reading source files.
- Stale layout `parents`: no evidence of a fix in 7.0.
- The defining class of `PUT /security/roles/{role_id}/groups` was not traced.
- All findings apply to 7.0.0rc3; the final tag may differ. The weekly `superset-drift.yaml` job should
  flag the final release.
