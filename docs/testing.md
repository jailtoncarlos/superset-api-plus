# Tests

How the test suite is organized, what each part checks and how to run it. Where each part runs in CI is
described in [ci-pipeline.md](ci-pipeline.md).

```
tests/
  conftest.py            loads the test stack .env into the environment (variables already set win)
  unit/                  offline: pure logic, conformance with the Superset sources, HTTP mocks only when justified
  integration/           against a real Superset (the compose stack or another instance)
    test_examples/       the example dashboards shipped with Superset
  fixtures/              excerpts of the Superset sources and UI captures, generated by bin/scripts
```

## Principles

- **Server behavior is tested against the real Superset**, in `tests/integration`. An HTTP mock is a guess about
  the server: a mocked test passed while the real 6.1.0 rejected the request.
- `tests/unit` mocks HTTP only when the real server cannot produce the condition deterministically (5xx and
  retry, asynchronous SQL Lab, TLS on the plain-HTTP stack) or to run offline in a hook (OpenAPI conformance);
  the module docstring says why. Pure logic (serialization, layout, buildQuery, enums) has no HTTP at all.
- Every bug fix comes with a test that fails before the fix. A defect found by the example dashboard tests also
  gets a unit test reproducing it.
- Prefer tests of the public contract (what the server stores or returns) over implementation details.
- Tests use synthetic payloads or the public Superset examples only.

## Running

```bash
uv sync --locked --all-extras
uv run pytest tests/unit                      # offline, a few seconds
uv run pytest tests                           # what the CI job `test` runs (integration tests skip without a Superset)
```

pytest logs at INFO level on the console (`log_cli` in `[tool.pytest.ini_options]` of `pyproject.toml`); add
`-q -o log_cli=false` for a quiet run.

### Conformance tests and fixtures

The library does not import Superset. It keeps versioned excerpts of the Superset sources and captures of the UI
in `tests/fixtures/`, and the conformance tests check the models against them:

| Fixture | Generated by | Checked by |
|---|---|---|
| `superset_openapi_<v>.json` | `bin/scripts/extract_openapi.py <v>` | `test_openapi_conformance.py`: payload fields, `POST_FIELDS`/`PUT_FIELDS`, routes |
| `superset_enums_<v>.json` | `bin/scripts/extract_superset_enums.py <v>` | `test_enum_conformance.py`, `test_extractors.py` |
| `example_layouts_<v>.json` | `bin/scripts/extract_example_layouts.py <v>` | `test_layout_validation.py` (the layout validation accepts every example layout) |
| `ui_references_<v>/` | `bin/scripts/extract_ui_references.py <v>` | `test_ui_references.py`, `test_build_query.py` |
| `ui_query_contexts_<v>/` | `bin/scripts/extract_query_contexts.py <v>` | `test_build_query.py` |
| `ui_defaults_<v>/` | `bin/scripts/extract_ui_defaults.py <v>` | `test_ui_defaults.py` |
| `ui_controls_<v>.json` | `bin/scripts/extract_ui_controls.py <v>` | `test_explore_form_data.py` |
| `example_query_contexts_<v>.json` | `bin/scripts/extract_example_query_contexts.py <v>` | `test_explore_form_data.py` and the example dashboard tests |

Fixtures are never edited by hand. The first three extractors read the Superset sources of a tag on GitHub
(`GITHUB_TOKEN`, when set, raises the API rate limit); the `ui_*` and `example_query_contexts` ones need the test
stack with `SUPERSET_LOAD_EXAMPLES=1` and `SUPERSET_URL`/`SUPERSET_USERNAME`/`SUPERSET_PASSWORD`, and all of them but
`extract_ui_references.py` also need Playwright with Chromium (`CHROME_PATH` selects the
browser). An extractor that finds nothing for a symbol fails instead of writing an empty set
(`test_extractors.py`). Moving to a new Superset version: [superset-version-bump.md](superset-version-bump.md).

## Integration tests

`tests/integration` runs against a real Superset: one module per area.

| Module | What it covers |
|---|---|
| `test_auth.py` | JWT login, renewal on 401, session mode (cookie + CSRF) |
| `test_errors.py` | exceptions by HTTP status, secrets kept out of the error logs |
| `test_charts.py` | chart search, reading, writing, data, export and import |
| `test_dashboards.py` | dashboard writing, chart association, layout and native filters |
| `test_data.py` | databases, datasets, saved queries and listing operators |
| `test_sql.py` | SQL Lab (`POST /api/v1/sqllab/execute/`) |
| `test_assets.py` | assets export and import (`/api/v1/assets/`) |

### The test stack

`docker-compose.yml` starts a disposable Superset (image and version from `.env`, default 6.1.0) on
`127.0.0.1:${SUPERSET_TEST_PORT}` (8089) plus a Postgres for the test data. All settings come from `.env`
(template: `.env.example`; `.env` is not versioned):

```bash
cp .env.example .env            # adjust SUPERSET_SECRET_KEY, credentials, port, version
docker compose -p superset-api-plus up -d --build
until curl -sf http://127.0.0.1:8089/health >/dev/null; do sleep 5; done
SUPERSET_INTEGRATION=1 uv run pytest -v tests/integration
docker compose -p superset-api-plus down -v
```

Use the compose project name `superset-api-plus` in every command, so only this stack is managed. The Docker
host may be shared with other projects: never run `docker system/image/volume prune`.

### Configuration

| Variable | Purpose |
|---|---|
| `SUPERSET_INTEGRATION=1` | run the integration tests against the local stack |
| `SUPERSET_URL` | run them against another instance instead (default `http://127.0.0.1:${SUPERSET_TEST_PORT}`) |
| `SUPERSET_USERNAME`, `SUPERSET_PASSWORD` | credentials (default: `SUPERSET_ADMIN_USERNAME`/`SUPERSET_ADMIN_PASSWORD` of the stack) |
| `SUPERSET_TEST_DATABASE_URI` | database the tests register (default: the stack Postgres, from `POSTGRES_*`) |
| `SUPERSET_SECRET_KEY` | secret of the stack; signs the expired token of the JWT renewal test |
| `SUPERSET_LOAD_EXAMPLES=1` | the stack loads the example dashboards (needed by `test_examples`) |
| `SUPERSET_EXAMPLES_REQUIRED=1` | `test_examples` fails instead of skipping when the examples are not loaded |

Without `SUPERSET_INTEGRATION` or `SUPERSET_URL` (and credentials), every test under `tests/integration` is
skipped. Tests that create users (marker `only_test_stack`) are skipped when `SUPERSET_URL` points to another
instance.

### Objects created by the tests

The tests create their own database, dataset, charts, dashboards, CSS templates and saved queries, named with
the prefix `zz-superset-api-plus-test`. The `cleanup` fixture removes them even when a test fails, so the
instance is left as it was.

## Example dashboard tests (`tests/integration/test_examples`)

One module per example dashboard shipped with Superset (`superset load_examples`): `test_deckgl_demo.py`,
`test_fcc_new_coder_survey.py`, `test_featured_charts.py`, `test_misc_charts.py`, `test_sales_dashboard.py`,
`test_slack_dashboard.py`, `test_usa_births_names.py`, `test_video_game_sales.py`, `test_world_health.py`.
The checks are shared (`checks.py`); for each dashboard:

- **round trip** (read only): the dashboard and each chart on it, read and re-serialized with `to_json()`, give
  what Superset stored (`position_json`, `json_metadata`, `params`, `query_context`);
- **chart copies**: each chart of a modeled viz_type is copied through the library, with the query context
  derived from its params, and must return the data the original shows in Explore. The reference is an
  independent capture of the query Explore sends for that chart
  (`tests/fixtures/example_query_contexts_6.1.0.json`, keyed by chart UUID), replayed against
  `/api/v1/chart/data`; a missing or stale capture fails instead of falling back to the library's query builder;
- **dashboard copy**: a dashboard created through the library with the original layout and `json_metadata`,
  chart ids remapped to the copies as the Superset import does, reads back like the original.

What is reported instead of failed (see the pytest warnings summary):

- `NotCoveredWarning`: charts of a viz_type the library does not model. They are copied through the raw API, so
  the dashboard copy points only to copies and the examples are never changed.
- `KnownDivergenceWarning`: charts whose copy returns other data and that have an open issue, listed in
  `known_divergences.py`. The check fails when one of them starts returning the data of the original, so the
  entry is removed when the issue is fixed.

Running them locally:

```bash
sed -i 's/^SUPERSET_LOAD_EXAMPLES=.*/SUPERSET_LOAD_EXAMPLES=1/' .env
docker compose -p superset-api-plus up -d --build      # loading the examples takes a few minutes
until curl -sf http://127.0.0.1:8089/health >/dev/null; do sleep 10; done
SUPERSET_INTEGRATION=1 uv run pytest -v tests/integration/test_examples -W always::UserWarning
```

On a stack that already has the examples, `docker compose -p superset-api-plus down -v` removes them with the
volumes; restart without `-v` to keep them between runs.

## Adding a test

- Pure logic or a rule from the Superset sources: `tests/unit`, no HTTP, citing the Superset source file the rule
  comes from.
- Anything the server decides (accepted fields, stored values, errors, permissions): `tests/integration`, in the
  module of its area, with objects named through `unique_name()` and registered in the `cleanup` fixture.
- A defect seen on an example dashboard: a unit test reproducing it, and, while the issue is open, an entry in
  `known_divergences.py` if the chart data differs.
